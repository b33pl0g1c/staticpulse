Orientation

What this project is

StaticPulse (staticpulse on the CLI) runs on a pull request, looks at what changed, and returns a single verdict a CI job can gate on: PASS, WARN, or FAIL. A deterministic scanner pipeline handles the pattern-matchable bugs; an LLM layer reasons about exploitability and proposes fixes it then verifies — but a plain-Python policy engine always makes the final call.

PASS · exit 0 WARN · exit 0 FAIL · exit 1
The one idea that matters

The LLM is only ever advisory. A plain-Python policy engine makes the final PASS / WARN / FAIL call. That keeps the gate reproducible, auditable, and fully functional even when every LLM provider is down — running with --no-llm gives the true decision.

Where it sits in the bigger picture

It is the static, reactive half of a pair. Its sibling project, agentic-pentester, is the dynamic, active half — an agent that attacks a running app. The long-term plan (Phase 3) bridges them: when the reviewer flags a reachable, endpoint-level issue, it can hand that hypothesis to the pentester to confirm by actually calling the endpoint.

How it works

The pipeline

The flow is linear and short, so it is a plain Python function rather than a graph framework — easier to read and debug while the domain is still being learned. A graph goes in later only if fan-out gets complex.

01 Diff git_diff.py
→
02 Scan semgrep_runner.py
→
03 Normalize + scope normalizer.py
→
04 Decide policy/engine.py
→
05 LLM review exploitability.py
Deterministic — runs today, no API key LLM — advisory second opinion, live

Two behaviours worth knowing on day one

  • Diff-scoping. Findings on files or lines the PR did not touch are dropped. Without it, the bot blames the author for the whole repo's existing backlog. A finding on a changed line stays; the same rule firing on an untouched file is discarded.
  • safe_join. A PR reviewer opens files whose paths come from scanners, diffs, and even LLM output — some ultimately derived from attacker-controlled PR content. A bare Path(repo) / file_path join lets ../../etc/passwd escape the repo root, so every file read routes through one path-traversal-safe helper where the check lives exactly once.

Changelog

What was done in Phase 0 + 1

Phase 0 stood up the skeleton; Phase 1 added the deterministic core. Both are complete and verified end-to-end with a real Semgrep scan running natively on Windows: the vulnerable fixture scans to FAIL and the clean one to PASS.

Three integration problems surfaced and got fixed

Each is a real-world integration lesson worth internalizing, because they will recur on any Python security tool that shells out to scanners.

Typer × Click

Installing Semgrep pulled Click 8.4, which breaks Typer 0.12. The fix is to move Typer forward, not pin Click back — typer>=0.15 works with the Click that modern Semgrep needs.

PATH resolution

shutil.which("semgrep") misses the venv's copy when the venv isn't activated. The runner now resolves the executable next to the interpreter instead.

Brittle keywords

The FAIL rule looked for sql-injection, but Semgrep names its rules formatted-sql-query. It WARNed until the keyword list was broadened — and a too-broad subprocess keyword was removed to protect precision.

Getting started

Run it yourself

# from the project root
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -e ".[dev]"
pip install semgrep

# scan a path — deterministic, no key required
staticpulse scan --repo tests/fixtures/sqli --no-llm --output report.json

# run the tests
pytest -q

Exit codes: 0 for PASS or WARN, 1 for FAIL, 2 for a terminal error — so a CI job's status reflects the gate directly.

Windows note: recent Semgrep (1.176+) runs natively and is verified here. If Semgrep is ever missing, staticpulse still runs: it reports the gap and returns a deterministic decision on whatever findings it has.

Design principles

The decisions that shape the code

A few principles recur throughout the codebase. Knowing them makes the rest read quickly.

PrincipleWhy it's built this way
Advisory LLM, deterministic decisionThe gate must be reproducible and auditable, so a plain-Python engine — never the model — makes the PASS/WARN/FAIL call.
Diff-scoping to the PR's changed linesA reviewer should judge the change, not the repo's backlog; findings outside the diff are dropped, and the eval harness proves it.
Stable content-hash finding IDsThe same issue keeps the same ID across re-pushes, which is what makes cross-push false-positive memory possible.
One safe file readerA path-traversal guard is easy to forget in one reader out of many, so all reads route through a single safe_join().
One shared budget trackerBuilt once in the orchestrator so a per-PR token/call cap is enforced in exactly one place, not multiplied per agent.
Evaluation on real git reposFixtures are assembled into two-commit repos at runtime, so the diff-scoping the eval measures is actually exercised.
What's next

The roadmap

Phases are a real build sequence — each depends on the one before. Two are done; four remain.

00SkeletonDone
  • CLI, Finding schema, stable IDs, the Semgrep runner, and the safe_join guard (tested first).
01Deterministic coreDone
  • Git diff + changed-line ranges, the normalizer's dedup and diff-scope, and the pure-Python policy engine. Verified: SQLi → FAIL, clean → PASS.
02LLM layer, done rightDone
  • Exploitability second-opinion per finding, with a hard rule that a critical secret is never downgraded.
  • One shared budget tracker created in the orchestrator, so the per-PR cap is enforced in exactly one place.
  • Content-addressed response cache so re-runs don't re-bill; second run is a full cache hit.
03DifferentiatorsDone
  • Verify-by-rescan patches (C1) — the LLM's fix is spliced into a throwaway copy and Semgrep re-runs; verified only if the finding disappears. Nothing touches the real tree. Confirmed live.
  • Cross-push false-positive memory (C4) — dismiss / restore a finding by its stable ID; later scans suppress it.
  • Pentester bridge (C5, seam) — handoff emits dynamically-confirmable findings for agentic-pentester to prove by calling the live app.
  • Deferred: inline PR review comments (needs a live PR) roll into Phase 5.
04Evaluation harnessDone
  • Fixtures are base/ + head/ trees; the harness builds a real two-commit git repo at runtime, so the diff-scoping the eval measures is genuinely exercised rather than skipped on a static directory.
  • staticpulse eval run reports recall / precision / decision accuracy / latency / tokens; --update-readme writes the table from the JSON so docs can't drift.
  • Honest result: 5/6 correct, recall 0.80, precision 0.80. The one miss (missing_authz) is a semantic bug no pattern scanner sees — the eval quantifies the recall ceiling.
05Ship itBuilt
  • A pull_request GitHub Actions workflow (scan-pr): posts a summary comment (marker-edited on re-push) + inline review comments, verified fixes as one-click suggestion blocks, and sets the CI status (FAIL blocks the merge).
  • Least-privilege permissions; fork-PR runs detect the read-only token, skip posting, and still set the status.
  • All rendering + client logic is unit-tested offline with a mocked API; live end-to-end runs on the first real PR.
